`@e2e-dev/limrun` is a hosted device provider for the mobile engine.
It creates a device for each worker, installs your app, and releases the device when the run ends.
Use the standard `app`, `screen`, and `expect` APIs to test your app's user flows.

## Install and authenticate

Install the integration alongside the mobile engine and its peers:

<CodeGroup>
```bash npm
npm install --save-dev e2e @e2e-dev/mobile @e2e-dev/limrun @limrun/api agent-device@0.21.22
```

```bash pnpm
pnpm add -D e2e @e2e-dev/mobile @e2e-dev/limrun @limrun/api agent-device@0.21.22
```

```bash bun
bun add -d e2e @e2e-dev/mobile @e2e-dev/limrun @limrun/api agent-device@0.21.22
```
</CodeGroup>

Set `LIMRUN_API_KEY` in the environment that starts e2e. In CI, store it as
a secret. Use a key with permission to create and control instances.
The provider reads the run's environment. It does not read the `lim login`
session or `LIM_API_KEY`.

The test runner needs Node.js and the package dependencies. For Android,
put `adb` from [Android SDK Platform-Tools](https://developer.android.com/tools/releases/platform-tools)
on `PATH`. No local emulator is needed. The iOS runner needs no local Xcode
or simulator. Build your app separately for an iOS simulator or as an Android
APK.

## Configure a target

Set `device: limrun()` on the mobile engine and point `appPath` at your build.
This config runs the SwiftUI app from the
[app-flow example](https://github.com/tester-army/e2e/tree/main/examples/with-limrun).

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';
import { limrun } from '@e2e-dev/limrun';

export default {
  targets: [{
    name: 'ios',
    engine: mobile({ platform: 'ios', device: limrun() }),
    app: {
      bundleId: 'dev.e2e.examples.swiftui',
      appPath: 'build/HelloApp.app',
    },
  }],
  workers: 2,
} satisfies E2EConfig;
```

For Android, use `platform: 'android'`, the app's package name as `bundleId`,
and an APK as `appPath`. Paths resolve against the project root.
The provider installs the build before tests start.

## Test an app flow

Use stable test IDs and visible text to fill forms and check their results.
This test corrects an empty submission and saves a screenshot of the greeting.

```ts title="tests/greeting.e2e.ts"
import { expect } from 'e2e';
import { test } from '@e2e-dev/mobile';

test('corrects an empty submission', async ({ app, screen }) => {
  await app.open();
  await screen.getByTestId('greet').click();
  await expect(screen.getByText('Enter a name first.', { exact: true })).toBeVisible();

  await screen.getByTestId('name').fill('Ada');
  await screen.getByTestId('greet').click();
  await expect(screen.getByText('Hello, Ada!', { exact: true })).toBeVisible();
  await expect(screen.getByText('Enter a name first.', { exact: true })).not.toBeVisible();
  await app.screenshot('greeting');
});
```

The [runnable example](https://github.com/tester-army/e2e/tree/main/examples/with-limrun)
uses the same five tests on SwiftUI and Compose apps.
It covers the initial form, validation recovery, trimmed input, repeated submissions, and app restart.
Its README includes build commands and a config with both targets. No AI key is needed.

## Record a run

Add `--video` to record every attempt:

<CodeGroup>
```bash npm
npx e2e run --video
```
```bash pnpm
pnpm exec e2e run --video
```
```bash bun
bunx e2e run --video
```
</CodeGroup>

Videos and screenshots are under `.e2e/`, alongside the run reports.

## Choose device options

| Option | Default | Purpose |
| --- | --- | --- |
| `region` | Limrun selects | Region preference, such as `eu` or `us-east1`. Capacity may cause overflow to another region. |
| `hardTimeout` | `1h` | Maximum device lifetime, including abandoned runs. Use a Go duration such as `30m` or `2h`. |
| `ios.model` | Limrun selects | `iphone` or `ipad`. |
| `android.model` | Limrun selects | `phone` or `tablet`. |
| `android.osVersion` | `15` | Android major version requested as a scheduling clue. |

Each worker gets an isolated agent-device daemon on the test runner and
one Limrun instance. The daemon uses agent-device's Limrun driver for app
control and recording. The integration requires the same agent-device
version that the mobile engine uses and checks that before allocation.

A device must become ready and finish installation within five minutes.
The provider cleans up after failed setup and the engine releases all
acquired devices when the run finishes or is interrupted. The provider renews idle driver leases while other targets run. The daemon
keeps an active device alive between commands; the hard timeout remains the
upper bound if the runner disappears. Choose a timeout longer than the run.

Instance IDs appear in progress output. Find a run's instances by the
`source=e2e` and `run=<run id>` labels in Limrun. Recordings use the normal
mobile artifact path, `video/video.mp4` inside each attempt directory.

## Check app compatibility

With agent-device 0.21.22, the Limrun iOS transport rejects keyboard actions
such as `locator.press('Enter')` with `UNSUPPORTED_CAPABILITY`.
Tap the app's submit button when the flow provides one.

Test the locators and libraries your app uses on its target runtime.
The greeting example demonstrates native form flows; it does not establish compatibility with every mobile framework or control.

## Supply camera input

Grant `camera: 'grant'` in `app.permissions` before opening the app.
Use the [camera example](https://github.com/tester-army/e2e/tree/main/examples/with-limrun-camera)
for a native scanner, video fixtures, and its target config.

Keep an MP4 or MOV in your project's fixtures directory. For a static QR
code or document, encode the image as a short video first. Image sources
and a `facing` option are not part of this API; the app chooses its camera.

```ts title="tests/scanner.e2e.ts"
import { expect } from 'e2e';
import { test } from '@e2e-dev/mobile';

const scanner = test.extend<{ cameraReady: void }>({
  cameraReady: async ({ device }, use) => {
    await device.camera.mockFeed({
      type: 'video',
      source: 'fixtures/valid-qr.mp4',
    });
    await use();
  },
});

scanner('accepts a known QR code', async ({ app, screen }) => {
  await app.open();
  await expect(screen.getByText('Code accepted')).toBeVisible();
});
```

The video loops by default. Set `loop: false` to play it once and hold the
last frame. `device.camera.clear()` restores the device's default input.
With no live input attached, that can mean no camera frames, rather than
frames showing a black or white image. Supply a blank video to test the
app's response to empty frames.

The engine clears injected media after every attempt, including failed
attempts and retries. It waits for an upload that outlived its action budget
before clearing, so that upload cannot replace the next test's input.
A provider without camera injection fails with `UNSUPPORTED_CAPABILITY`.

Call camera methods in fixtures or between agent steps. Keep them out of
custom agent tools so cached agent steps replay against the same input.
Camera injection changes the device's input; it does not grant camera
permission or change application code that disables simulator capture.

Android video injection requires Android 15 or newer. The provider requests
Android 15 by default. Use videos without an audio track for camera-only
tests; Android camera injection also feeds the video's audio into the
microphone. When combining controls, inject a silent camera video first,
then set the microphone audio.

Some camera libraries disable simulator capture in their own build. For
example, `expo-camera` 17.0.10 in Expo SDK 54 compiles out the iOS simulator
capture path. Such a build needs an app-side change or a library version
that supports simulator capture. Injecting a feed cannot restore code
that was left out of the binary. Validate the exact library and OS used by
your app before adopting a camera suite.

## Supply microphone input

Grant `microphone: 'grant'` in the target's `app.permissions`. Keep a WAV
or MP3 fixture in your project and start the app's capture before injecting
one-shot audio. `mockAudio()` returns when playback starts, without waiting
for the recording to finish. It loops by default; `loop: false` plays once
and then returns to silence. Playing another file replaces the current one.

The [microphone example](https://github.com/tester-army/e2e/tree/main/examples/with-limrun-microphone)
measures tones through AVAudioEngine on iOS and AudioRecord on Android:

```ts title="tests/microphone.e2e.ts"
import { expect } from 'e2e';
import { test } from '@e2e-dev/mobile';

test('captures known microphone audio', async ({ device, app, screen }) => {
  await app.open();
  await screen.getByRole('button', { name: /listen/i }).click();
  await device.microphone.mockAudio({ source: 'fixtures/440.wav' });
  await expect(screen.getByText('440 Hz detected')).toBeVisible();
  await device.microphone.clear();
  await expect(screen.getByText('Silence')).toBeVisible();
});
```

`clear()` stops injected audio and returns to silence. The engine also clears
audio after every attempt, including failures and retries. File paths resolve
against the project root. Missing files fail before upload, and providers
without microphone injection report `UNSUPPORTED_CAPABILITY`.

Keep microphone setup in fixtures or between agent steps, so replayed agent
steps see the same input. Injection supplies audio to the normal capture
pipeline; it does not bypass microphone permission or implement speech
recognition. Assert on your app's recorded audio or transcription separately.

The native example checks two distinct tones, silence, replacement, one-shot
playback, explicit clearing, and silence in the next attempt. Speech services
and third-party recording libraries need their own compatibility tests.

## Test in-app purchases

Use an ad hoc signed iOS simulator build and a local `.storekit` file created
in Xcode. Limrun's remote Xcode builds use ad hoc signing by default for
simulator apps. No App Store Connect catalog or sandbox Apple account is
needed for these local tests.

Apply the catalog before opening the app. If the app is already running,
call `app.restart()` after changing the catalog so its product cache refreshes.
The [StoreKit example](https://github.com/tester-army/e2e/tree/main/examples/with-limrun-storekit)
contains a native StoreKit 2 app and catalogs for consumables, a premium
unlock, and a monthly subscription.

```ts title="tests/storekit.e2e.ts"
import { expect } from 'e2e';
import { test } from '@e2e-dev/mobile';

test('shows the local product catalog', async ({ device, app, screen }) => {
  await device.storekit.setConfig({
    bundleId: 'dev.e2e.storekit',
    source: 'fixtures/Catalog.storekit',
  });
  await app.open();
  await expect(screen.getByRole('button', { name: 'Buy Premium' })).toBeVisible();
});
```

The example uses a Limrun iPad and `transition: 2000` for StoreKit sheet
animations. Drive the purchase sheet with normal `screen` locators and
assert on your app's purchase result or entitlement. Keep catalog setup in fixtures or
between agent steps. `source` resolves against the project root; missing
files, invalid bundle IDs, and invalid JSON fail before upload. Xcode owns
the catalog schema; e2e checks that the file contains a JSON object.

`device.storekit.clearConfig(bundleId)` removes that app's local catalog.
The engine also clears every catalog it touched after each attempt,
including failures and retries. An upload that outlives its action timeout
must settle before cleanup. Android and providers without StoreKit support
report `UNSUPPORTED_CAPABILITY`.

**Clearing a catalog does not erase transactions or entitlements.** A worker
reuses its simulator for the run. Use consumables or separate product IDs
for independent purchase cases, and start a new run when a scenario needs
empty purchase history. Clearing returns StoreKit to its normal sandbox
behavior; it does not install an empty catalog. Use an empty `.storekit`
file when you need deterministic zero-product behavior.

Purchase-sheet locators were verified on iPad with iOS 26.4. On iPhone 16 Pro
with iOS 26.4, the Purchase button can disappear from the accessibility tree
while remaining visible; that automation issue also reproduces with the
Limrun SDK directly. Use the iPad example for the verified purchase flows.

These controls configure local StoreKit testing. They do not expose refund,
subscription-expiry, transaction-reset, or payment-failure commands.
Local transactions cannot validate an Apple production receipt or your
server's App Store integration. Verify your app's StoreKit wrapper and
simulator runtime separately, especially legacy StoreKit 1 receipt and
restore flows.
